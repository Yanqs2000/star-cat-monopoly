# 3B 日期、公司与董事权源码证据（静态核对中）

本文件只记录已经从 `docs/modernization/evidence/source/play.swf/scripts/` 核对的原版脚本事实，供 3B 规则和测试设计使用。它不是 3B 实现或原版整局动态验证。原始 SWF 保持只读；银行交易和股票交易分别见同批独立证据文件。

## 日期从哪里来，何时推进

- 主程序 `frame_6/DoAction.as:59-65` 在开局调用一次 `new Date()`，取得年、月、日、星期（日为 0）。当前 3A `createGame(humans, seed, initialWeekday)` 只保存 `WorldState.weekday` 与 `elapsedDays`，尚无年月日；现代界面只注入一次星期。3B 必须将开局年月日作为一次性输入，与星期保存在同一权威可序列化状态中；重试和恢复不能再次读取系统时间。
- `frame_5/DoAction.as:1445-1608` 的 `goback()` 在当前玩家收尾后先处理资金耗尽和胜负分支；若 `day_id==1` 且后面没有未破产玩家，会先打开银行月结动画。随后轮到最后一人转回第一人时，在 `_loc6_==1` 分支中推进日期。这个前置银行动画的完成条件和跨日顺序必须在银行证据与受控回放中核实，不能仅以代码出现的顺序推断它已经结算。
- 换日分支的静态调用次序是：`checkMoney()`；日加 1；若越过当月天数，则月加 1、日置 1、`month_sd_pg()`、`price_pg()`；若进入下一年，年加 1、月置 1；星期加 1，回到星期日时执行 `week_sd_pg()`；接着 `day_sd_pg()`、`asset_pg()`、`jin_pg()`。见 `frame_5/DoAction.as:1581-1610`。因此股票月变化、周变化、日变化和神灵/限制倒计时有可观察的先后关系；3B 只实现自己需要的财务推进，但不能再建第二套每日 tick。
- 原版月份长度在 `frame_5/DoAction.as:1583-1588` 写死为 `[31,28,31,30,31,30,31,31,30,31,30,31]`。`phase-1-findings.md:110` 将固定二月列为 B-04 疑点。3B 首先把它作为原行为记录，跨闰年修正必须先取得原运行差异和用户可检验的测试；不能直接用 JS `Date` 自动替换并称忠实。
- 原版 `frame_4/DoAction.as:2999-3087`：`day_sd_pg()` 只遍历公司 ID 1…12，依次更新旧价、当日价格、涨跌、最高/最低和待购股数；`week_sd_pg()` 改每家公司字段 7，`month_sd_pg()` 改字段 8，各有自己的随机调用。ID 0、13…15 不走这些日/周/月更新。各字段含义及 RNG/取整公式由股票证据文件逐行锁定。
- `frame_4/DoAction.as:3105-3124` 的 `jin_pg()` 对全部玩家的限制天数与神灵天数分别减 1（仅正数）。当前 `controller.ts:470-471` 在四名玩家最后一人收尾时只调用 `advanceWorldDay`。3B 接入金融日期时，应以同一次整轮 wrap 为唯一提交点，在已有状态基础上有序扩展，而非让 UI 或股票模块自行前进日期。

## 公司出生与地点交互

- `frame_5/DoAction.as:660-694` 在开局按角色 ID attach `gufen{id}` 公司建筑，位置来自所选出生区 `startpdate[][2]`；对应公司是 `stockdate[playerdate[pid][7]]`，写入该玩家的初始股份 `stockdate[companyId][10+pid]=[3000,10]`、经营权字段 19、建筑记录字段 20，并改动该公司的初始价格和三条 `builddate` 公司地块。公司资源与地图位置因此要从原表确定，不能按角色座次推断同一公司或随意摆放。
- `frame_3/DoAction.as:494` 的四个出生区公司图片原点分别为 `(1988,251)`、`(1765,1395)`、`(305,1479)`、`(530,330)` 原版像素；它们不是玩家实际站立格。只读 JPEXS 26.2.1 对原 `play.swf` 的探针确认 `gufen1…12` 都是 30 fps、根 1 帧精灵，符号 ID 依次为 `186,180,213,183,189,192,204,198,195,201,207,210`。源边界随角色不同，例如 1 为 `[-1780,1780,-2540,1280]`、12 为 `[-2080,2080,-2060,1540]` twips。`scripts/export-company-assets.py` 按源哈希锁定和逐张边界核对导出 `public/modern/assets/companies/` 的 12 张透明 PNG 与清单；`MapScene.ts` 根据角色 ID 和出生区把图片放在上述原点，以源边界左上偏移保留锚点。暂存联系表 `.analysis-cache/3b-company-assets/contact-sheet.png` 和生产构建全图 `.analysis-cache/acceptance-3b/start-companies-1440x1000.png` 已目视核对，源 SWF 未修改。
- 源公司遮挡深度为 `30000 + y*3000/YL + x*30/XL`（`frame_5:666-667`）；现代场景统一使用 `y/40*100+x/56`，等于移除共同常量并除以正数 30，保留与同基准角色/建筑的先后关系，图片内部偏移不参与排序。
- `frame_4/DoAction.as:1778-2092` 的 `end_pg1()` 读取当前地点的公司 ID 与 `stockdate[id][19]` 经营权人。无人经营、自己经营、其他玩家经营走不同分支。其他人落在公司地点时，普通公司可按掷出的倍数乘设施费；公共事业分支可按拥有房屋数乘设施费。费用汇入公司字段 17，`paybill_pg` 先扣现金，不足部分扣存款（`frame_4:2080-2093`）。3B 的公司地点不能直接复用 2C 的普通住宅租金。
- 公司收费和董事结果使用原版 `show` 对话框，认购确认复用同一画框的 `yesno1`（同源文件 `1914-1938,1945-1975,2105-2132`）。完成审计补入 `show` 符号 1515 的停留帧 20：只提取 depth 1 的符号 1510（原平移 `[-3960,-3480]` twips）和 depth 3 的符号 1512（原平移 `[0,300]`），排除动态示例文字。逻辑边界 `[-3960,3960,-3480,3400]`，原滤镜外扩每边 6 px，未缩放导出为 408×356，图片原点偏移 `[-204,-180]`。`ExportCompanyUiAssets.java` 只构造内存单帧副本，`export-company-ui-assets.py` 锁定原 SWF 哈希与 JPEXS 26.2.1，不保存 SWF。现代公司面板使用该原图框并把权威余额/股份投影为可读文字，认购数量仍走 Vue 命令；图片失败接入现有序列化恢复，原逐帧出入动画未迁移。
- 普通公司的倍数来自 `yntz2` 原版精灵（符号 1602），并非一枚骰子：完整只读导出的 `DefineSprite_1602_yntz2/frame_1,frame_10,frame_17/DoAction.as` 各执行两次 `random(6)+1`；第 17 帧把最后两枚点数之和写入 `r`，第 50 帧以 `_root.yesno_id=r` 提交给上述收费分支。因此一次费用动画消耗六次随机调用，最终倍数为 **2…12**。现代规则保留六次调用与最后两枚点数，界面显示两骰和；目前没有复现 50 帧逐帧掷骰动画，这属于明确视觉差异。
- 购买地点剩余股份时，`paystock_pg` 用 `单价×选择股数` 扣当前玩家现金，增加 `stockdate[companyId][10+pid]` 的持有股数，按 `int(100×(新支付额+原股数×原均价)/新股数)/100` 更新持仓均价，并减少 `builddate[companyParcel][9]` 的待购股数（`frame_4:2094-2103`）。计数器允许的最大值、现金不足时能否走到此函数、与普通股票市场买卖的差异，必须在股票证据中独立核对；本段不能单独证明所有交易边界。
- `director_pg` 先写公司地块所属人 `builddate[dz][0]=pid` 和临时 `ceo_id=pid`（`frame_4:2105-2114`）；`end_pg1` 的收尾分支再把临时值写入 `stockdate[id][19]`（`frame_4:1849-1854,2072-2078`）。`end_pg1:2015-2078` 的挑战分支比较当前玩家与其他持股者的股数；相等时不获得“严格领先”资格。原版流程另需显示确认和结果，不能只按现金最多判定董事。
- `frame_4/DoAction.as:2876-2921` 的 `asset_pg()` 以 ID 1…15 的持股数×当前价计入资产，再加现金、存款和住宅价值，扣已用信用及贷款；公司建筑是否另作独立资产价值要按该函数的实际加项确认，不得重复计算。
- 月初银行动画 `DefineSprite_2527_bank/frame_2/DoAction.as:12-69` 对公司 ID 1…15 中 `stockdate[i][17] > 0` 的记录，先为每个持股玩家累计其**股数本身**，再加 `int(公司累计盈利 × 该玩家持股数 / 全部玩家持股数)`，清空该公司盈利字段；最后只把累计结果加到未破产玩家的存款。若只按盈利比例分红，漏掉了股数本身的额外入账；这部分是源规则产生的新存款，不可错误宣称资金总量守恒。原脚本没有显式处理 `总持股数==0` 且盈利正数的分母边界，需结合原表和可达状态判断，而不能猜测。具体与银行贷款/信用月结的顺序待银行证据确认。

## 目前不能直接推断的内容

1. `goback` 使用 `znmu` 的反编译结果与已验证的正常换人不一致（`phase-2b-evidence.md` 有指令级探针）。3B 不能由此认为日期永不前进，也不能私自“修正拼写”；要用受控跨日回放确定触发时序。
2. 月初银行弹窗、信用月结、贷款/存款利息和公司收入分配的精确先后，需与银行取证和原版受控样例交叉核对。
3. 公共事业 ID 13…15 的经营权与交易资格、公司总股数/剩余股数的守恒，需结合股票源表与地点脚本核对。`asset_pg` 遍历到 15 不等于它们都是普通可买股票。
4. 公司 `gufen1…12` 已导出并在生产构建全图核对；仍需在真实行走和公司格交互回放中检查角色遮挡和费用/认购状态同步。
